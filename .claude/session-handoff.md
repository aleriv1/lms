- Гасить всё, что запустил, до конца сессии: дев-сервер под `tsx watch` переживает собственное падение и держит порт, а следующий запуск падает с `EADDRINUSE` и выглядит дефектом кода. Проверка — `netstat -ano | grep ":4000" | grep LISTENING`, снятие — `taskkill //PID <номер> //T //F`. Контейнер `lms-mongo` гасить не надо. То же правило для Codex — AGENTS.md (8).

## Принятые решения

- TypeScript strict везде; общий пакет Zod-схем = валидация + типы + резолвер RHF. Дублировать схемы в `client/` или `server/` нельзя.
- CSS Modules + собственные примитивы. Готовые UI-киты не берём.
- MongoDB + mongoose с самого начала, без промежуточного JSON-хранилища. База описана `docker-compose.yml` в корне, поднимается `npm run db:up`, к `npm run dev` не цепляется: дев-сервер не должен молча дёргать Docker и падать невнятно при выключенном движке.
- Версии актуальные, а не «как в примерах курса»: React 19, Node 24 LTS, Express 5 (ТЗ v1.2). Кураторы версий не задают. Express 5 выбран из-за штатной передачи ошибок async-обработчиков в централизованный обработчик — обёртка `catchAsync` запрещена.
- Окружение: Node 24 через nvm (активна), MongoDB контейнером в Docker, в систему не ставится. Codex работает локально в той же папке — база у него и у разработчика одна.
- `shared/` — `@lms/shared` на zod 4, TS NodeNext с `.js` в импортах, сборка в `dist/`.
- Сообщения валидации на русском живут во входных схемах `shared/`; клиент их не переводит.
- Сервер API-only: клиент собирается Vite и раздаётся отдельно, ТЗ раздачи статики сервером не требует. Поэтому `notFound` отвечает контрактным JSON на любой непойманный путь, а не только под `/api`.
- `.env.example` лежит в `server/`, рядом с местом, где `import "dotenv/config"` его читает (`cwd = server/`). Корневого `.env` нет и не заводим.
- Store Redux Toolkit и централизованная обработка `401` — срез 02, не 01: store без редьюсера невалиден, заглушка была бы мёртвым кодом. Маршрут добавляет тот срез, который его обслуживает; пустых страниц по разделу 6 ТЗ не заводим.
- Минимальный `npm run seed` (три пользователя по ролям) — срез 02, полный демо-набор раздела 12 ТЗ — срез 10.
- `activityWeeks` и `recentActivity` на Этапе 1 — пустые массивы (помечено в `shared/src/learning.ts`), то же для `userStatisticsSchema.recentActivity`. `activeUsersCount` на Этапе 1 — по `LessonProgress.updatedAt` за 30 дней, с срезом 12 источник меняется на `ActivityEvent`.
- Смоук-тест схем (33 случая) лежит вне репозитория, переносится в `shared/` как контрактный тест в срезе 11.
- После каждого среза с логикой Claude пишет разбор на 15–20 строк для защиты.

## Открытые вопросы

Форма пункта: вопрос — где лежал бы ответ — что блокирует. Без указателя на источник пункт не заводится: записать указатель значит сходить и проверить. Ответ найден — строка переезжает в «Принятые решения» той же правкой, а не удаляется.

- Формат сдачи (репозиторий, архив, деплой). Источник: кураторы; в `materials-for-thoughts/` требований к сдаче нет, ТЗ (10) описывает только команды проверки. Не блокирует код, нужен к финалу.

## Ревью срезов (три слоя)

1. Машина: `typecheck`, `lint`, `build`, `test` + сверка со списком файлов среза. Гоняет сам Codex до конца среза.
2. Codex со свежим контекстом по чек-листу Claude: соответствие Zod-контракту, необработанные состояния, мёртвый код, пропущенные пункты.
3. Claude — только риск-зоны и замысел: права доступа и обход по URL, серверные расчёты прогресса и баллов, утечки в ответах API, состояния loading/empty/error, расхождение с промптом.

Codex сдаёт срез одним коммитом и самоотчётом в `.codex/reports/slice-NN.md`, затем останавливается: без push, без amend. Коммиты ревью ложатся сверху — видно, что сдал Codex и что изменило ревью. Закрыт срез или нет — решает ревью, сам он это не объявляет. Claude читает отчёт и точечные куски диффа, не дифф целиком.

## Когда переходить в новую сессию

Три шва, у каждого своя причина — не смешивать:

- **Ревью и приёмка среза — всегда свежая сессия. Причина: независимость.** Сессия, писавшая промпт, защищает свои формулировки и читает код через свой замысел. Экономия тут ни при чём.
- **Промпт-правка по итогам ревью — в той же сессии, что нашла дефекты.** Кто нашёл, тот дешевле всех и опишет. Так сделан `slice-01-fix.md`.
- **Промпт следующего среза — свежая сессия. Причина: экономия.** Написание промпта многоходовое, и каждый ход тащит весь накопленный контекст заново; класть его поверх сессии ревью значит платить за чужой рабочий набор на каждом ходу. Корпуса почти не пересекаются: ревью читает дифф и отчёт, промпт — план среза, разделы ТЗ и `shared/`. Побочная выгода: если промпт пишется из файлов и файлов хватает, значит их хватит и Codex.

Промпт среза 02 написан в сессии приёмки как разовое исключение: корпус уже был загружен до того, как решение обсуждалось.

Плюс общие поводы: этап завершён и результат записан в файл; меняется тип работы; контекст начал суммироваться или ответы поплыли.
