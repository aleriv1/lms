# Срез 04, серверная половина — уроки

Спека для сессии-реализации. Исполнитель — Claude. Читается вместе с
`shared/src/lessons.ts` и файлами из раздела «Состав среза»; ТЗ не
пересказывается, разделы цитируются номерами.

Клиент в этой половине не трогается ни одним файлом. Серверная половина
сдаётся отдельным коммитом до того, как кто-либо откроет `client/`.

Порядок авторитетов обычный: `technical-specification.md` → `shared/` →
`AGENTS.md` → эта спека. Спека не спорит с ТЗ; если спорит — это дефект
спеки, и он идёт в самоотчёт, а не разрешается на месте.

## 1. Что даёт

Автор курса и администратор заводят урок внутри курса, редактируют его,
меняют порядок уроков одной операцией, публикуют и снимают публикацию.
`GET /courses/:courseId` начинает отдавать реальное оглавление, каталог —
реальное число уроков, а публикация курса — проверять условие ТЗ 4.2 про
опубликованный обязательный урок, а не отказывать всегда.

Обучающийся уроков ещё не видит: `/learning/*` — срез 07.

## 2. Ловушки контракта

Обе проверены запуском `updateLessonBodySchema.parse(...)` на собранном
`shared/dist`, а не выведены из чтения кода.

**`.partial()` не снимает `.default()` внутри поля.**
`updateLessonBodySchema.parse({ title: "abc" })` возвращает

```json
{ "title": "abc", "resourceLinks": [], "isRequired": true, "testId": null }
```

Три дефолта — `resourceLinks`, `isRequired`, `testId`. PATCH только с
названием, написанный «в лоб», очистил бы список ссылок и вернул
обязательность в `true`. Ровно та же ловушка сработала на курсах
(`updateCourseBodySchema` подставляет `description: ""`).

Лечится тем же приёмом, что уже стоит в `routes/courses.ts`: до валидации
запоминаются ключи сырого тела (`captureCourseUpdateFields`), и присваивается
только то, что клиент действительно прислал. В уроках это middleware
называется `captureLessonUpdateFields`, кладёт ключи в
`response.locals.lessonUpdateFields` и стоит между `validate(params)` и
`validate(body)`. Дублирование с курсами оставляем: чинится оно в `shared/`
в срезе 11 (у update-схем не должно быть дефолтов вовсе), и до тех пор две
явные копии честнее одной преждевременной абстракции.

**`videoUrl` при создании обязателен.** `optionalHttpUrlSchema` —
`union([httpUrl, literal("")]).transform(...).nullable()`; `.nullable()`
пропускает `null`, но не `undefined`. Поэтому `createLessonBodySchema`
без `videoUrl` не проходит валидацию: клиент обязан прислать `null` или
`""`. В `updateLessonBodySchema` поле действительно необязательно.
Схема курса устроена так же (`coverUrl`), так что это не новый дефект, а
свойство контракта — но клиентская половина о нём должна узнать из промпта.

## 3. Маршруты

Все требуют `requireAuth` и `requireRole("teacher", "admin")`, и все — прав
на конкретный курс через существующий `loadOwnedCourse` (автор или
администратор, иначе 403).

| Метод и путь | Тело | Ответ |
|---|---|---|
| `POST /courses/:courseId/lessons` | `createLessonBodySchema` | `201` + `lessonSchema` |
| `PATCH /courses/:courseId/lessons/:lessonId` | `updateLessonBodySchema` | `200` + `lessonSchema` |
| `DELETE /courses/:courseId/lessons/:lessonId` | — | `204` |
| `POST /courses/:courseId/lessons/:lessonId/publish` | — | `200` + `lessonSchema` |
| `POST /courses/:courseId/lessons/:lessonId/unpublish` | — | `200` + `lessonSchema` |
| `POST /courses/:courseId/lessons/reorder` | `reorderLessonsBodySchema` | `200` + `courseDetailSchema` |
| `GET /lessons/:lessonId` | — | `200` + `lessonSchema` |

**Почему чтение одного урока лежит вне курса.** ТЗ 6 фиксирует клиентский
маршрут `/manage/lessons/:lessonId/edit` — без `courseId` в URL. ТЗ 9.2 столь
же буквально фиксирует `POST /courses/:courseId/lessons/:lessonId/publish`.
Оба ограничения выполняются одновременно только так: единственное чтение
одного урока — плоское, все изменения — в контексте курса, а `courseId` для
них страница берёт из загруженного урока. ТЗ 9 называет свой список
минимально необходимым, поэтому добавление `GET /lessons/:lessonId` — не
спор с ТЗ. Второго, курсового чтения одного урока не заводим: два маршрута
с одинаковым смыслом — это дублирование, а не симметрия.

Списочного маршрута уроков нет вовсе. Оглавление приходит в
`courseDetailSchema.lessons`, и это же снимает вопрос про конверт
`createListResponseSchema`: оглавление — не страница списка, пагинации у
него нет.

**Монтирование.** `courseLessonsRouter` создаётся с `mergeParams: true` и
монтируется в `routes/courses.ts` как
`coursesRouter.use("/:courseId/lessons", courseLessonsRouter)` — сразу после
строки с `requireAuth`, чтобы проверки роли наследовались. Плоский
`lessonsRouter` монтируется в `routes/index.ts` на `/lessons` и ставит
`requireAuth, requireRole(...)` себе сам.

**Валидация параметров.** `validate(schema, "params")` подменяет
`request.params` результатом разбора, а Zod-объект отбрасывает неизвестные
ключи. Поэтому в дочернем роутере схема параметров обязана называть **оба**
поля — `courseId` и `lessonId`, — иначе `courseId` из `mergeParams`
пропадёт до обработчика. Для `POST /courses/:courseId/lessons` и `reorder`
схема — только `courseId`.

Коллизии `reorder` с `:lessonId` нет: методы и глубина путей разные.

## 4. Модель `Lesson`

`server/src/models/Lesson.ts`, по образцу `models/Course.ts`.

Поля: `courseId` (ObjectId, ref `Course`, required), `title` (String,
required, trim), `order` (Number, required), `content` (String, required),
`durationMinutes` (Number, required), `videoUrl` (String, default `null`),
`resourceLinks` (массив поддокументов `{ title, url }` с `_id: false`),
`isRequired` (Boolean, default `true`), `status` (String, enum
`LESSON_STATUSES`, default `"draft"`), плюс `timestamps`.

**`testId` в модели не хранится.** ТЗ 8.3 его в составе `Lesson` не
называет, а ТЗ 8.4 кладёт связь в `Test.lessonId` — и комментарий в
`shared/src/lessons.ts` говорит то же: поле формы лишь задаёт связь,
хранится она на стороне теста. Поэтому `testId` в ответах — производное
значение, и до среза 05, где появляется модель `Test`, оно всегда `null`.

Индексы:

- `{ courseId: 1, order: 1 }`, `unique: true` — правило ТЗ 4.2 на уровне
  базы, а не только в обработчике;
- `{ courseId: 1, status: 1 }` — под запрос числа опубликованных
  обязательных уроков при публикации курса.

«Активный урок» из ТЗ 4.2 читается как «существующий»: у урока состояний
всего два, `draft` и `published`, архивного нет. Уникальность номера держится
по всем урокам курса независимо от статуса. Иначе публикация черновика могла
бы упасть на конфликте номера, а оглавление в ТЗ 7.12, где черновики видны
вместе с опубликованными, не имело бы полного порядка.

Экспортируются `toLesson(lesson): Lesson` и `toLessonSummary(lesson):
LessonSummary` — те же две функции-проекции, что у курса, обе ставят
`testId: null`.

## 5. Инварианты и коды отказа

Новых кодов не заводим: всё выражается через `API_ERROR_CODES`.

| Ситуация | Ответ |
|---|---|
| Курс не найден | `404 not_found` (из `loadOwnedCourse`) |
| Курс чужой, вызывающий — преподаватель | `403 forbidden` (из `loadOwnedCourse`) |
| Урок не найден, либо принадлежит другому курсу, чем в пути | `404 not_found` |
| Номер урока занят другим уроком курса | `409 conflict` |
| Публикация уже опубликованного / снятие с черновика | `409 conflict` |
| Публикация урока без названия или содержания | `422 unprocessable`, `fields` по полям |
| Тело `reorder` — не полный список уроков курса | `422 unprocessable` |
| В теле `reorder` повторяются номера | `409 conflict` |
| `testId` не `null` | `404 not_found` («Тест не найден») |

Про `testId`: до среза 05 коллекции тестов не существует, поэтому любой
присланный идентификатор указывает на несуществующий тест, и `404` —
честный ответ, а не выдуманное правило. В срезе 05 эта ветка заменяется
настоящим поиском `Test` по `_id` + `courseId` (ТЗ 7.13: тест должен
принадлежать тому же курсу) и записью `Test.lessonId`.

Про урок из чужого курса: `loadOwnedCourse` уже отвечает `403` на чужой
курс, поэтому по паре `courseId` + `lessonId` из разных курсов до урока
дело не доходит. `404` остаётся для случая, когда курс свой, а урока в нём
нет. Плоское `GET /lessons/:lessonId` сначала ищет урок (`404`), затем
зовёт `loadOwnedCourse(lesson.courseId, user)` (`403`) — то есть о
существовании чужого урока преподаватель узнаёт ровно так же, как узнаёт о
существовании чужого курса. Расхождения с уже принятым поведением тут нет.

**Снятие публикации не трогает прогресс.** Модели `LessonProgress` ещё нет,
поэтому инвариант выражается запретом: ни один обработчик этого среза не
пишет и не удаляет ничего, кроме документов `Lesson`. Удаление урока —
жёсткое; отказ удалять урок с сохранённым прогрессом принадлежит срезу 07,
где появляется, что проверять.

Дырки в нумерации после удаления допустимы: порядок задаётся сортировкой по
`order`, непрерывности ТЗ не требует, и перенумерация чужих уроков при
удалении одного была бы неожиданным побочным эффектом.

## 6. Порядок уроков

`server/src/lessons/lessonOrder.ts` — чистые функции плюс тонкая обёртка над
записью.

**Занятость номера при создании и правке.** Перед сохранением —
`Lesson.exists({ courseId, order, _id: { $ne: lessonId } })`, при находке
`409 conflict`. Проверка не отменяет уникального индекса: между проверкой и
записью есть окно, поэтому ошибка Mongo `11000` ловится и переводится в тот
же `409`. Хелпер `isDuplicateKeyError(error): boolean` живёт здесь же.

**Переупорядочивание.** Тело по контракту содержит полный список уроков
курса. `planReorder(existing, requested)` — чистая функция, бросает
`AppError`:

- множество `lessonId` в теле не совпадает с множеством уроков курса
  (пропущен, лишний или повторён) → `422 unprocessable`;
- номера в теле повторяются → `409 conflict`.

Возвращает окончательные пары «урок → номер».

Записывается это двумя последовательными `bulkWrite` — иначе перестановка
двух соседних уроков упирается в уникальный индекс на промежуточном шаге:

1. всем урокам курса `{ $mul: { order: -1 } }` — номера уходят в минус.
   Отрицательные значения уникальны между собой (отрицание инъективно) и
   заведомо не сталкиваются с положительными;
2. каждому уроку `{ $set: { order } }` из плана. Все документы в этот
   момент отрицательные, целевые номера различны — столкновений нет.

Транзакции не используем: Mongo поднят одиночным контейнером, транзакции
требуют replica set. Разрыв между фазами оставил бы отрицательные номера, и
чинится он повторной отправкой той же операции — именно потому тело обязано
быть полным списком, а не диффом. Это ограничение называется в разборе.

## 7. Санитизация содержимого

`content` хранится как **HTML**, очищенный сервером. ТЗ 7.13 разрешает и
Markdown, но выбор одного формата снимает вопрос, кто и когда рендерит, а
требование ТЗ 7.6 «содержимое выводится безопасно, без исполнения
произвольных скриптов» выполняется в единственной точке — на записи.

Зависимость: `sanitize-html@^2.17.0`, типы `@types/sanitize-html@^2.16.1`,
в `server/package.json`. Решение принято здесь; реализация его не
пересматривает.

`server/src/lessons/sanitizeContent.ts` экспортирует
`sanitizeLessonContent(raw: string): string`. Конфигурация — белый список,
всё неназванное отбрасывается (`disallowedTagsMode: "discard"`):

- теги: `p`, `br`, `hr`, `strong`, `em`, `u`, `s`, `h2`, `h3`, `h4`, `ul`,
  `ol`, `li`, `blockquote`, `code`, `pre`, `a`, `img`, `table`, `thead`,
  `tbody`, `tr`, `th`, `td`;
- атрибуты: `a` — `href`, `title`; `img` — `src`, `alt`, `title`; больше
  никаких, поэтому обработчики событий (`onclick` и прочие) исчезают как
  неназванные;
- схемы ссылок: `http`, `https`, `mailto`. `data:` не разрешена ни для
  `img`, ни для чего-либо ещё;
- `transformTags` добавляет всем `a` атрибуты `target="_blank"` и
  `rel="noopener noreferrer nofollow"`.

Вызывается функция **в обработчике**, между валидацией и сохранением, на
`POST` и на `PATCH` — там, где содержание присутствует в присланных полях.
Не сеттером схемы Mongoose и не middleware: очистка — заметный шаг
обработки, и прятать её от читателя маршрута незачем.

**Пустота после очистки.** Zod проверяет сырой ввод, где `<script>x</script>`
непуст, а после очистки от него не остаётся ничего. Поэтому очищенное
значение проверяется ещё раз: если после `trim` оно пусто —
`422 validation_error` с `fields: [{ field: "content", message: "Содержание
обязательно" }]`. Сообщение совпадает с тем, что в схеме, чтобы клиент
показал его тем же способом.

Длина после очистки повторно не проверяется: экранирование сущностей
(`&` → `&amp;`) способно добавить несколько символов, а
`LESSON_CONTENT_MAX_LENGTH` — ограничение на ввод, не на хранение. Обрезать
уже принятый материал из-за экранирования было бы хуже, чем сохранить его
чуть длиннее.

`title` урока и `resourceLinks[].title` не санитизируются намеренно: это
текстовые узлы, React экранирует их сам, а прогон текста через
HTML-очиститель исказил бы легальные `<` и `&`. Ссылки уже ограничены
`httpUrlSchema` протоколами `http`/`https`.

## 8. Правки в уже написанном

**`server/src/courses/publishRules.ts`.** Сейчас `collectPublicationIssues`
безусловно добавляет замечание про урок, из-за чего опубликовать курс
нельзя вообще. Сигнатура становится

```ts
collectPublicationIssues(course, publishedRequiredLessonsCount: number)
```

и замечание добавляется только при нуле. Функция остаётся чистой; счёт
делает маршрут запросом
`Lesson.countDocuments({ courseId, status: "published", isRequired: true })`.

**`server/src/routes/courses.ts`.**

- `GET /:courseId` отдаёт настоящее оглавление: уроки курса, отсортированные
  по `order` по возрастанию, спроецированные `toLessonSummary`. `tests`
  остаётся пустым — срез 05.
- `POST /:courseId/publish` считает опубликованные обязательные уроки и
  передаёт число в `collectPublicationIssues`.
- `lessonsCount` перестаёт быть нулём. В `GET /` — одна агрегация по уже
  выбранной странице курсов:
  `Lesson.aggregate([{ $match: { courseId: { $in: ids } } }, { $group: { _id: "$courseId", count: { $sum: 1 } } }])`,
  где `ids` — курсы текущей страницы. Коллекция целиком не читается.
  В остальных ответах — `countDocuments` по одному курсу. Считаются уроки
  всех статусов: в управляющем каталоге автору нужен объём курса, а не его
  опубликованная часть.

**`server/src/routes/index.ts`** — монтирование `lessonsRouter` на `/lessons`.

  даёт своё замечание.

## 11. Приёмка

`npm run typecheck`, `npm run lint`, `npm run build`, `npm run test` —
зелёные. Плюс проверка руками при поднятой базе, потому что модульные тесты
базу не трогают:

1. создать урок в своём курсе — `201`, статус `draft`;
2. создать второй урок с тем же `order` — `409`;
3. `PATCH` только с `title` — `resourceLinks` и `isRequired` не изменились
   (главная ловушка среза);
4. отправить `content` с `<script>alert(1)</script>` вокруг текста —
   сохранён очищенный HTML; `content` из одного `<script>` — `422`;
5. `reorder` с перестановкой двух соседних — `200`, оглавление в новом
   порядке; тот же вызов без одного урока — `422`;
6. опубликовать урок, затем курс — публикация курса проходит; снять
   публикацию урока и повторить — `422 course_not_publishable` с
   замечанием про уроки;
7. чужой курс из-под второго преподавателя: создание урока — `403`,
   `GET /lessons/:lessonId` чужого урока — `403`.

Дев-сервер после проверки гасится: `netstat -ano | grep ":4000" | grep
LISTENING`, затем `taskkill //PID <номер> //T //F`.

## 12. Что этот срез не делает

Ничего для обучающегося (`/learning/*` — срез 07), никакой связи с тестами
кроме отказа `404` (срез 05), никакой защиты урока с сохранённым прогрессом
от удаления (срез 07), никакого клиента.

Клиентской половине (промпт `.codex/prompts/slice-04-client.md` пишется
после приёмки этой) достаются как заданные: обязательный `videoUrl` при
создании, `testId` только `null`, подсказка следующего свободного `order`
считается на клиенте из оглавления, а `reorder` возвращает курс целиком —
перерисовывать оглавление надо из ответа.
