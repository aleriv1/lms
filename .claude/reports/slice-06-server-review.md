# Срез 06, серверная половина — ревью

Свежая сессия. Спека `.claude/specs/slice-06-server.md` разбиралась как
подсудимый: восемь решений её раздела 11 сверены с ТЗ, а не код со спекой.
Гейт после правки зелёный целиком; сервер поднимался один раз для проверки
одной гипотезы, браузер не открывался.

## 1. Дефект: обход запрета ТЗ 4.1 идентификатором в верхнем регистре

**Найдено и подтверждено запросом, а не выведено из чтения.**
`collectSelfModificationIssues` сравнивала `actor.id !== targetUserId`
строками, а `objectIdSchema` — это `/^[0-9a-fA-F]{24}$/`: верхний регистр
проходит валидацию, MongoDB приводит обе формы к одному `ObjectId`.

Прогон на живой базе, администратор `admin@lms.local`:

- `PATCH /api/admin/users/6a96b8cb…c7` с `role: "teacher"` → `422
  self_modification_forbidden`, как задумано;
- тот же запрос на `…C7` в верхнем регистре → `200`, и единственный
  администратор системы понизил себя до преподавателя.

Это прямое нарушение ТЗ 4.1, а не доопределение спеки: правило существует
ровно для этого случая. Учётная запись восстановлена в базе сразу после
проверки (`role: admin`, `status: active`, имя).

**Исправлено коммитом ревью** — сравнение регистронезависимое, вынесено в
`isSameUser`, добавлен юнит-тест «верхний регистр — тот же пользователь»
(сервер 56 → 57 тестов).

Класс шире одного файла: небезопасно любое сравнение идентификатора **из
пути** со значением из базы. Проверены все такие места — второе и последнее
(`courseAccess.ts:29`) сравнивает `authorId` из базы с `user.id` из сессии,
обе стороны приходят из Mongo в нижнем регистре, обхода нет. Радикальная
альтернатива — `.transform(v => v.toLowerCase())` прямо в `objectIdSchema`,
чтобы класс закрылся навсегда; не сделана здесь, потому что это правка
контракта, а она идёт отдельным коммитом и с ревизией всех потребителей.

## 2. Восемь решений раздела 11 против ТЗ

| № | Решение | Вердикт |
|---|---|---|
| 1 | `DELETE` отвечает `200` с телом | Принято |
| 2 | Общий код `unprocessable` на два отказа | Принято |
| 3 | Архивирование себя запрещено наравне с блокировкой | Принято |
| 4 | Повторное назначение создаёт новую запись | Принято с обязательным хвостом в срез 07 |
| 5 | Фильтр по группе — подстрока | Принято |
| 6 | Архивные пользователи из списка не прячутся | Принято |
| 7 | `PATCH` отдаёт детальную карточку | Принято, идёт в промпт клиента |
| 8 | Состав добавлений в сид | Принято |

**1.** ТЗ 9.5 называет `204` статусом «успешная операция без тела», а не
обязанностью `DELETE`. Снятие назначения — смена состояния: строка остаётся,
`revokedAt` ставит сервер. Отдать `204` значило бы заставить клиент
придумывать серверную метку времени или делать рефетч — ровно та ошибка, за
которую платили срезы 04 и 05.

**2.** ТЗ 9.5 требует «стабильный машинный код» и список полей, а не
отдельный код на каждую причину. `API_ERROR_CODES` подходящего кода не
содержит, обе ситуации различаются по `fields[].field` (`courseId` против
`userId`), и клиент показывает их одинаково — у поля формы. Заводить коды
стоило бы, если бы клиент по ним ветвился; он не будет.

**3.** ТЗ 4.1 называет блокировку и понижение, а формулирует через
«собственную **активную** учётную запись», то есть через сохранение
активности. `requireAuth` отвечает `401 account_blocked` на любой статус,
кроме `active`, — архивирование себя отбирает доступ ровно как блокировка.
Доопределение только запрещает, ни один сценарий ТЗ его не требует.

**4.** ТЗ 4.3: «Снятие назначения не удаляет накопленный прогресс. При
повторном назначении прогресс восстанавливается». Сейчас нарушения нет —
прогресса не существует, `progressPercent` равен нулю по факту. Но решение
навязывает срезу 07 условие, которого спека не назвала: **прогресс обязан
считаться по паре `userId + courseId` из `LessonProgress`, а не по
`assignmentId`** — иначе новая запись покажет ноль там, где ТЗ требует
восстановления. Второе следствие того же решения: частичный индекс и
проверка `exists` смотрят только на `status: "active"`, поэтому
**завершённое назначение не мешает создать новое активное** на ту же пару.
ТЗ 4.3 запрещает лишь повторное *активное*, так что это законно, но срез 07
получит пользователя с записями `completed` и `active` одновременно, и
новая при пообъектном расчёте мгновенно окажется стопроцентной. Оба пункта —
хвостом в `slice-plan.md` под срез 07.

**5.** ТЗ 7.14 требует фильтр по группе, ТЗ 1.4 и 4.1 запрещают группы как
сущность. Списка групп для выпадающего поля не существует, значит фильтр
может быть только текстовым; подстрока ведёт себя как фильтр по категории
курса. Точное равенство заставило бы администратора набирать «Смена А»
посимвольно верно.

**6.** ТЗ 4.1 делает архивирование заменой удаления, ТЗ 7.14 даёт фильтр по
статусу без умолчания. Спрятать архивные записи значило бы спрятать
единственный результат «удаления» от того, кто его сделал.

**7.** Контракт `shared/` схемы ответа `PATCH` не задаёт, так что
противоречия нет, а карточка вместо `publicUserSchema` снимает у клиента
повод на рефетч. Условие: промпт клиентской половины обязан типизировать
ответ `PATCH` как `AdminUserDetail`, иначе назначения в карточке протухнут
после правки имени.

**8.** ТЗ 12 (демонстрационный набор) закреплён за срезом 10; здесь
добавлен минимум под чек-листы, идемпотентность сохранена, повторный прогон
ничего не дублирует. Оговорка отчёта про недогон существующих записей верна
и важнее, чем кажется: см. пункт 3 ниже.

## 3. Состояние базы разработчика

Проверялось попутно, кодом не вызвано, но чек-лист об этом должен знать.

- У `student@lms.local` в базе лежало имя, испорченное перекодировкой, — след
  ручной проверки прошлой сессии (`curl` в PowerShell), а не сервера.
  Проверено: тот же `PATCH` телом в UTF-8 из файла возвращает и сохраняет
  «Обучающийся Петров» корректно. Запись починена через API, заодно
  проставлена группа «Смена А», которой сид не догнал.
- `slice02fix.…@example.test` из среза 02 всё ещё в списке — уйдёт со срезом 10.
- Два назначения на `student@lms.local` (`active` и `revoked`) оставлены
  намеренно, как и написано в отчёте: на них будет проверяться клиент.

## 4. Что проверено и признано верным без замечаний

Права (`requireAuth` + `requireRole("admin")` на роутере, вложенный роутер
наследует), отсутствие утечек (`toPublicUser` без `passwordHash`, оба
`populate` с явным списком полей), порядок проверок в `POST` (404 → 422 →
409), чужое назначение по прямой ссылке неотличимо от несуществующего,
`activeAssignmentsCount` одной агрегацией по странице, немедленная потеря
доступа заблокированным. Отступления от спеки из раздела 2 отчёта — все три
обоснованы, спор со спекой решён в пользу кода.
