# Срез 02 — разбор для защиты

**Вопрос: почему роль и статус читаются из базы на каждом запросе, а не из токена?**

Токен подписывается один раз и живёт 7 дней (`signSessionToken`, `expiresIn: "7d"`).
В его payload лежит только `sub` — идентификатор пользователя; `jwt.sign({}, ...)`
не кладёт туда ничего больше. Это сделано намеренно.

Всё, что попало бы в токен, замерзает в момент выдачи. ТЗ 3.1 требует, чтобы
блокировка учётной записи гасила уже открытую сессию. Если бы `status` жил в
токене, заблокированный пользователь продолжал бы работать до его истечения —
до недели. Списка отзыва у нас нет, сократить этот срок нечем. То же с ролью:
понижение преподавателя администратором оставило бы ему прежние права до
переполучения токена.

Поэтому `requireAuth` на каждом защищённом запросе делает `User.findById(userId)`
и проверяет `user.status !== "active"` уже по свежей записи. База — единственный
источник прав; токен отвечает только на вопрос «кто», никогда — «что ему можно».

Цена — один поиск по первичному ключу на запрос: индексированный, в том же пуле
соединений, на фоне сетевого round-trip незаметный.

Альтернатива, оставляющая токен авторитетным, — короткоживущий access + refresh:
второй токен, эндпоинт ротации и хранилище отзыва. Это ответ на проблему
масштаба, которой у проекта нет.

Три ветки отказа — токен не разобран, пользователь удалён, учётная запись
заблокирована — все чистят cookie (`clearSessionCookie`), чтобы клиент не завис
в полуавторизованном состоянии. Коды при этом разные: `unauthorized` против
`account_blocked`, чтобы интерфейс отличал «войдите заново» от «вас
заблокировали».
