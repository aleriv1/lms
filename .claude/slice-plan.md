# План вертикальных срезов

Порядок реализации. Один срез — одна задача Codex, закрывается самоотчётом по
`AGENTS.md` (8). Файл не пересказывает ТЗ: у каждого среза указаны разделы ТЗ и
схемы `shared/`, по которым срез проверяется.

Обновлено: 2026-09-02

## Как читать срез

- **Даёт** — что можно показать после среза. Если показать нечего, срез нарезан плохо.
- **Сервер / Клиент** — состав работ, не список файлов. Файлы фиксирует промпт.
- **Контракт** — схемы `shared/`, которым обязан соответствовать обмен.
- **Риск-зоны** — что Claude смотрит руками на третьем слое ревью.
- **Разбор** — 15–20 строк к защите, пишет их хвостом сессия ревью, закрывшая срез.
- **Хвосты** — долги, заведённые прошлыми срезами и адресованные этому. Хвост живёт здесь, а не в хэндоффе: хэндофф переписывается каждую сессию, а хвост обязан дождаться своего среза и попасться на глаза тому, кто его открывает. Закрыл — вычеркнул строку.

Срез не начинается, пока не закрыт предыдущий: зависимости строго линейны.
Параллельного исполнения нет и оно бы не помогло: узкое место — не время, а
токены, а две одновременные сессии платят ориентировку дважды.

**Кто пишет половину.** Серверная — Claude по спеке в `.claude/specs/`,
клиентская — Codex по промпту в `.codex/prompts/`. Это распределение по двум
бюджетам, а не по сложности. Срезы 05–09 идут двумя половинами каждый; 10 — одной
сессией Codex.

## Цикл 1 — вертикальное ядро (Этап 1 ТЗ, раздел 18.1)

### Срез 01 — Каркас репозитория и дизайн-система

Единственный срез без бизнес-логики: он даёт всем следующим общую землю.

- **Даёт:** `npm install`, `npm run dev`, `npm run build`, `typecheck`, `lint` проходят; клиент открывается, сервер отвечает на health-роут и подключается к MongoDB.
- **Сервер:** bootstrap Express, подключение Mongoose, конфиг из переменных окружения, `.env.example`, централизованный обработчик ошибок в формате `apiErrorSchema`, журналирование запросов, middleware валидации по Zod-схеме (принимает схему, отдаёт `422` со списком полей), health-роут.
- **Клиент:** Vite + React 19, роутер с теми маршрутами, которые срез уже обслуживает (`/` и 404), единый API-клиент, файл дизайн-токенов, базовые компоненты `Button`, `Input`, `Select`, `Textarea`, `Checkbox`, `Modal`, `Loader`, `EmptyState`, `ErrorState`.
- **Store Redux Toolkit переехал в срез 02:** store без единого редьюсера невалиден, а заглушечный слайс — мёртвый код. Store появляется вместе с `authSlice`. Там же централизованная обработка `401`: до среза 02 нет сессии, которую можно потерять. Пустых страниц-заглушек по разделу 6 ТЗ срез тоже не создаёт — маршруты добавляет тот срез, который их обслуживает.
- **Контракт:** `apiErrorSchema`, `API_ERROR_CODES`, `createListResponseSchema`.
- **Риск-зоны:** формат ошибки от обработчика; отсутствие секретов в репозитории; `strict` во всех трёх workspace.
- `Table` и `Pagination` появляются в срезе 03, где для них есть первый потребитель. Разбор не пишется: бизнес-логики нет.

### Срез 02 — Аутентификация, роли, профиль

- **Даёт:** регистрация, вход, выход, боковая навигация по роли, `/forbidden` и 404, просмотр и редактирование профиля, смена пароля. Блокировка администратором мгновенно валит чужую сессию.
- **Сервер:** модель `User` с уникальным индексом по email, хеширование пароля, JWT в `httpOnly` cookie, `requireAuth` с перечитыванием статуса из базы на каждом защищённом запросе, `requireRole`, маршруты 9.1.
- **Клиент:** `authSlice`, `ProtectedRoute` и проверка роли, страницы `/login`, `/register`, `/forbidden`, 404, layout с боковой навигацией по роли, `/profile`, `/profile/edit`.
- **Контракт:** `registerBodySchema`, `loginBodySchema`, `sessionResponseSchema`, `publicUserSchema`, `updateProfileBodySchema`, `changePasswordBodySchema`.
- **Риск-зоны:** `passwordHash` не покидает сервер ни в одном ответе; статус читается из базы, а не из токена; неавторизованный уходит на вход, авторизованный без роли — на `/forbidden`; двойная отправка формы.
- **Дополнительно:** минимальный `npm run seed` — администратор, преподаватель, обучающийся. Без него следующие срезы нечем проверять руками. Полный демо-набор раздела 12 ТЗ — срез 10.

### Срез 03 — Курсы: CRUD и жизненный цикл

- **Даёт:** преподаватель заводит курс, редактирует свой, публикует и архивирует; каталог с поиском, фильтрами, сортировкой и серверной пагинацией; администратор правит чужой курс, преподаватель — нет.
- **Сервер:** модель `Course`, индексы поиска, проверка авторства на каждой операции с конкретным курсом, `GET /courses` со всеми параметрами запроса, `POST`, `GET /:id`, `PATCH`, `DELETE`, `publish`, `archive`. Публикация требует условий 4.2 ТЗ, иначе `422 course_not_publishable`. Удаление опубликованного курса с назначениями или прогрессом — `409 course_delete_forbidden`.
- **Клиент:** `/manage/courses` (таблица, поиск с задержкой 500 мс, фильтры, сортировка, пагинация), `/manage/courses/new`, `/manage/courses/:id/edit`, подтверждение удаления и архивирования в модальном окне. Появляются `Table` и `Pagination`.
- **Контракт:** `coursesQuerySchema`, `courseListItemSchema`, `courseDetailSchema`, `createCourseBodySchema`, `updateCourseBodySchema`, `createListResponseSchema(courseListItemSchema)`.
- **Риск-зоны:** обход авторства прямым запросом к API; условия публикации считает сервер; пагинация не тянет коллекцию целиком; четыре состояния каталога.
- **Разбор:** проверка прав на уровне сущности, а не только маршрута.

### Срез 04 — Уроки

- **Даёт:** уроки внутри курса: создание, редактирование, порядок, публикация и снятие публикации.
- **Сервер:** модель `Lesson`, уникальность `order` среди активных уроков курса (`409 conflict`), CRUD в контексте курса, `publish` и `unpublish` отдельными действиями, очистка HTML/Markdown содержимого перед сохранением, переупорядочивание. Снятие публикации не трогает сохранённый прогресс.
- **Клиент:** список уроков на странице курса, `/manage/courses/:courseId/lessons/new`, `/manage/lessons/:lessonId/edit`, поля обязательности, длительности, ссылок на материалы.
- **Контракт:** `lessonSchema`, `lessonSummarySchema`, `createLessonBodySchema`, `updateLessonBodySchema`, `reorderLessonsBodySchema`, `resourceLinkSchema`.
- **Риск-зоны:** санитизация содержимого; уникальность порядка; авторство курса проверяется и на операциях с уроком.
- **Разбор:** зачем санитизация и где она стоит.

### Срез 05 — Тесты: создание и редактирование

- **Даёт:** преподаватель собирает тест урока и итоговый тест курса, редактирует вопросы и варианты.
- **Сервер:** модель `Test` со встроенными вопросами, `version` как счётчик правок, CRUD в контексте курса, серверная проверка правил вопроса из 4.4 ТЗ.
- **Клиент:** `/manage/courses/:courseId/tests/new`, `/manage/tests/:testId/edit` — динамическая форма вопросов и вариантов на React Hook Form, валидация по схеме из `shared/`, ошибки рядом с полями.
- **Контракт:** `createTestBodySchema`, `updateTestBodySchema`, `questionInputSchema`, `questionOptionInputSchema`, `testSchema`, `testSummarySchema`.
- **Риск-зоны:** правила вопроса проверяются сервером, а не только формой; `passingScore` по умолчанию 70.
- **Разбор:** одна схема на форму и на сервер — что это даёт.

### Срез 06 — Пользователи и назначения

- **Даёт:** администратор ищет пользователя, меняет роль и статус, назначает и снимает курс.
- **Сервер:** `GET /admin/users` с поиском, фильтрами и пагинацией, `GET` и `PATCH /admin/users/:id`, запрет понижения и блокировки собственной учётной записи (`422 self_modification_forbidden`), удаление пользователя с историей как архивирование, модель `CourseAssignment`, назначение только опубликованного курса, запрет повторного активного назначения (`409 assignment_exists`), снятие назначения без потери прогресса.
- **Клиент:** `/admin/users`, `/admin/users/:userId`, назначение курса из карточки пользователя, подтверждения в модальном окне.
- **Контракт:** `adminUsersQuerySchema`, `adminUserListItemSchema`, `adminUserDetailSchema`, `adminUpdateUserBodySchema`, `assignmentSchema`, `createAssignmentBodySchema`.
- **Риск-зоны:** назначение черновика или архивного курса прямым запросом; администратор не режет права себе; статус `archived` вместо удаления.
- **Разбор:** почему назначение — отдельная сущность со статусом, а не поле в пользователе.

### Срез 07 — Обучение: курсы, уроки, прогресс

- **Даёт:** обучающийся видит назначенные курсы, открывает доступный урок, завершает его; прогресс считает сервер и он переживает перезаход.
- **Сервер:** модель `LessonProgress`, `GET /learning/me`, `GET /learning/courses/:courseId`, `GET /learning/courses/:courseId/lessons/:lessonId`, `POST /learning/lessons/:lessonId/start` и `/complete`. Процент и состояние доступности урока считает сервер: доля завершённых обязательных опубликованных уроков, необязательные не в счёт. Обращение к неназначенному курсу — `403 course_not_assigned`, к заблокированному уроку — `403 lesson_locked`, завершение урока с обязательным тестом без проходного результата — `422 lesson_test_required`.
- **Клиент:** `/learning`, `/learning/courses/:courseId` с оглавлением и состояниями уроков, страница урока с материалами и кнопкой завершения.
- **Контракт:** `learningOverviewSchema`, `learningCourseCardSchema`, `learningCourseSchema`, `learningLessonSchema`, `learningLessonItemSchema`, `lessonProgressResponseSchema`, `lessonAccessStateSchema`.
- **Риск-зоны:** главный срез по правам — обход блокировки прямой ссылкой, доступ к чужому и неопубликованному, расчёт процента только на сервере, клиент не шлёт готовый процент.
- **Разбор:** где живёт расчёт прогресса и почему не на клиенте.

### Срез 08 — Прохождение теста

- **Даёт:** обучающийся проходит тест, видит результат, урок с обязательным тестом закрывается только проходным баллом.
- **Сервер:** `GET /learning/tests/:testId` без признака правильности вариантов, `POST /learning/tests/:testId/attempts` — снимок вопросов в попытке, расчёт балла на сервере, `multiple` засчитывается только при полном совпадении набора, номер попытки, влияние на завершение урока и курса.
- **Клиент:** `/learning/tests/:testId`, экран результата с баллом и статусом, возврат к курсу.
- **Контракт:** `learnerTestSchema`, `learnerQuestionSchema`, `submitAttemptBodySchema`, `attemptResultSchema`, `testAttemptSummarySchema`.
- **Риск-зоны:** утечка правильных ответов в выдаче до отправки; частичные баллы; повторное нажатие не плодит попытки-дубли; снимок вопросов сохраняется целиком.
- **Разбор:** зачем попытка хранит снимок вопросов.
- **Хвосты:**
  - **Показатели теста у обучающегося — заглушки среза 07 по факту, а не по недоделке.** `toLearningTestRef` и `findFinalTestState` в `server/src/routes/learning.ts` отдают `passed: false`, `bestScore: null`, `attemptsCount: 0`: попыток не существовало. Здесь они считаются по `TestAttempt`, и это правка одного файла в трёх местах.
  - **`POST /learning/lessons/:lessonId/complete` отказывает `lesson_test_required` безусловно** — раз у урока есть привязанный тест, значит зачтённой попытки нет. Условие дополняется до «и нет зачтённой попытки». Флага «тест обязателен» у урока нет и заводить его срез 07 отказался: всякий тест урока обязателен (спека 07, решение 1).
  - **Курс с итоговым тестом не завершается никогда,** пока попыток нет, и назначение не переходит в `completed`. Переход стоит в обработчике завершения урока; после среза 08 его обязан уметь делать и обработчик отправки попытки — иначе курс, у которого последним закрывается итоговый тест, останется `active` на ста процентах.
  - **Входов в тест на экранах обучающегося нет, и их обязан завести этот срез.** ТЗ 7.6 требует, чтобы уроку с обязательным тестом предлагали пройти тест; срез 07 показывает `TestSummaryCard` и строку «Урок завершается прохождением теста», но никакой кнопки — маршрута `/learning/tests/:testId` тогда не существовало, и ссылка на несуществующий маршрут была бы хуже её отсутствия. Правка клиентская и в двух местах: `TestSummaryCard.tsx` (или вызывающие его `LearningLessonPage.tsx` и `LearningCoursePage.tsx`) получает ссылку на тест. Без неё срез 08 сдаст экран, на который нельзя попасть иначе как по прямому URL.

### Срез 09 — Главная администратора и базовая статистика

- **Даёт:** реальные счётчики на `/admin`, сводная таблица обучающихся, карточка статистики ученика, блок статистики в личном кабинете. Пункт 11 критериев приёмки в базовом объёме.
- **Сервер:** `GET /admin/dashboard`, `GET /admin/statistics`, `GET /admin/statistics/users/:userId`, `GET /learning/me/statistics` — агрегация по назначениям, прогрессу и попыткам.
- **Клиент:** `/admin`, `/admin/statistics`, `/admin/statistics/users/:userId`, статистика в `/profile`.
- **Контракт:** `adminDashboardSchema`, `adminStatisticsQuerySchema`, `adminStatisticsResponseSchema`, `adminStatisticsRowSchema`, `courseProgressStatSchema`, `userStatisticsSchema`, `learnerStatisticsSchema`, `learnerCourseStatSchema`.
- **Что Этап 1 отдаёт по этим схемам:** `activityWeeks` и `recentActivity` — пустые массивы, фильтры раздела 7.15 приходят в срезе 12. `activeUsersCount` на Этапе 1 считается по `LessonProgress.updatedAt` **и** `TestAttempt.submittedAt` за последние 30 суток: «отправка теста» названа учебным действием в ТЗ 7.16, а попытка итогового теста курса не задевает ни одной строки прогресса урока. С появлением `ActivityEvent` в срезе 12 источник меняется на события.
- **Риск-зоны:** агрегаты считаются запросами к базе, а не перебором коллекций в памяти; обучающийся видит только собственную статистику.
- **Разбор:** агрегация в MongoDB против выборки всего и подсчёта в Node.
- **Хвосты:** все три закрыты серверной половиной — решения в
  `.claude/specs/slice-09-server.md` (7.1 отозванное назначение, 3 и 6
  последняя и лучшая попытки, 7.3 `totalLearningMinutes`), подтверждения
  поведением — в `.claude/reports/slice-09-server.md` (3 и 6).

### Срез 10 — Демо-данные, README, сдача Этапа 1

- **Даёт:** чистое окружение поднимается по README и наполняется одной командой. Этап 1 закрыт.
- **Состав:** полный `npm run seed` по разделу 12 ТЗ (корпоративное обучение: вводный инструктаж по охране труда, правила технической эксплуатации, работа с диспетчерской системой), README с окружением, установкой, запуском, сборкой, тестами и перечнем демо-учёток, краткое описание API, проверка `.env.example`.
- **Риск-зоны:** сид воспроизводим и идемпотентен; в репозитории нет паролей и строк подключения; демо-пароли не годятся для production.
- **Хвосты:**
  - `DELETE /courses/:courseId` (`server/src/routes/courses.ts:195–215`) удаляет один документ, хуков на моделях нет: уроки осиротели ещё в срезе 03, со срезом 05 к ним добавились тесты. ТЗ 4.2 про содержимое удаляемого черновика молчит, нарушения нет — в базе остаётся мусор, и это заметная асимметрия с запретом удалять урок с тестом.
  - **Сид не выполняет ТЗ 12 по четырём пунктам, и каждый стоил непроверенного сюжета в срезе 08.** Архивного курса нет вовсе (три курса: черновик и два опубликованных) — решение «на архивном курсе тест читается, но не сдаётся» непроверяемо в принципе. В основном опубликованном курсе четыре урока против «не менее пяти». Единственный вопрос типа `multiple` лежит в черновиковом курсе (`seed.ts:186`), который никому не назначен, — центральное правило ТЗ 4.4 о полном совпадении набора не проходимо через learner API ни на одном сюжете. Ни одного теста на уроке, который может быть заблокирован, — а спека 08 называет отказ `lesson_locked` главной дырой своего среза. Полный сид закрывает ТЗ 12 целиком, а не по одному пункту под текущую нужду: срез 11 упрётся в те же четыре состояния. Заведено ревью серверной половины 08.
  - `server/dist/` собирает тесты и `setupTests.js` вместе с исходниками — чистить здесь.
  - Сид идемпотентен по принципу «есть email — пропускаем» и не догоняет уже существующие записи: поле, дописанное поздним срезом, на наполненной базе не применяется (так `groupName` у `student@lms.local` в срезе 06 не проставился). Полный сид раздела 12 ТЗ либо умеет пересоздавать набор с нуля, либо предупреждает об этом в README.
  - В рабочей базе разработчика лежит `slice02fix.…@example.test` — след ручной проверки среза 02. На поведение не влияет, но портит счёт `total` в списке пользователей.
- Разбор не пишется.

## Цикл 2 — Этап 2 ТЗ (раздел 18.2) и приёмка

Срез 11 входит в Этап 1 (ТЗ 18.1 требует автотесты по ключевым сценариям).
**Срезы 12–14 (Этап 2) не делаются — решено на ревью серверной 09.** ТЗ 18.2
разрешает их не выполнять, если состав недоделанного зафиксирован явно; запись
состава пишет сессия, закрывающая срез 11 (хвост ниже). Описания срезов 12–14
остаются здесь не планом, а адресом: хвост, привязанный к такому срезу, — это
хвост, который никто не заберёт, и он обязан попасть в запись 18.2.

### Срез 11 — Автотесты ключевых сценариев

Раздел 13 ТЗ в части Этапа 1: расчёт балла и прогресса, вход и отказ при неверных данных, ролевой middleware, CRUD курса, назначение, запрет доступа к неназначенному и чужому курсу, отправка теста и сохранение попытки. Сюда же переезжает смоук-тест схем (33 случая) как контрактный тест в `shared/`.

- **Хвосты:**
  - `shared/`: у update-схем не должно быть `.default()` — `.partial()` их не снимает, и оба маршрута PATCH обходят это, запоминая ключи сырого тела до валидации (`captureCourseUpdateFields`, `captureLessonUpdateFields`). ## Хвосты, привязанные к файлу, а не к срезу

Эти долги ждут не своего среза, а своей правки: каждый называет файл и уезжает
комментарием к строке тогда, когда очередная задача этот файл откроет. Жили в
хэндоффе, пока не выяснилось, что там их читает каждая сессия, а нужны они той
одной, которая эти файлы трогает. Пишешь промпт или спеку — сверься со списком
файлов среза.

- **Сравнивать идентификатор из пути со строкой опасно: `objectIdSchema` — это `/^[0-9a-fA-F]{24}$/`.** Верхний и нижний регистр проходят валидацию и дают один `ObjectId`, поэтому строковое сравнение пути с сессией обходится сменой регистра. Один такой случай уже стоил дефекта прав в срезе 06 и починен на месте (`server/src/admin/selfModification.ts`, регистронезависимо, с тестом). Второе сравнение проекта (`courseAccess.ts:29`) безопасно: обе стороны приходят из базы. Второе попадание — клиентское: `AdminUserDetailPage` сравнивал идентификатор пути с загруженным и на верхнем регистре не сходился никогда; починено там же. Радикальное лечение — `.transform(v => v.toLowerCase())` в самой `objectIdSchema`, но это правка контракта, и она стоит ревизии всех потребителей; отдать её тому срезу, который откроет `shared/src/common.ts`.

- **Ту же ветку «идентификатор пути против загруженного» держат четыре принятых страницы** — `LessonCreatePage:55`, `LessonEditPage:103`, `TestCreatePage:53`, `TestEditPage:118`: строгое сравнение и `ErrorState` на несовпадении. Оба следствия те же, что в срезе 06: карточка предыдущей сущности между монтированием и первым эффектом уходит в отказ вместо загрузки, а адрес с идентификатором в верхнем регистре не сходится никогда. `TestEditPage:89` в том же файле уже показывает `Loader`, так что конвенция в коде разошлась. Лечится тем же, чем в `AdminUserDetailPage.tsx`: сравнение через `toLowerCase()` и `Loader` вместо `ErrorState`. Срезы 04–05, отдать той правке, которая эти файлы откроет.
- **Санитайзер стоит на маршруте, а не на модели, и seed его минует.** `prepareContent` вызывается только в `server/src/routes/courseLessons.ts` (создание и правка урока); `server/src/scripts/seed.ts` пишет `content` прямо в модель. Материал сидов наш и безобиден, поэтому дефекта нет, но гарантия, на которую ссылается комментарий у `dangerouslySetInnerHTML` в `LearningLessonPage.tsx`, покрывает путь записи через API, а не «любую строку в базе». Лечится переносом очистки в `pre("save")` модели `Lesson` — тогда утверждение становится безусловным. Отдать той правке, которая откроет `models/Lesson.ts`.
- **Форма урока не умеет отвязать тест, и это временно.** `PATCH` урока считает присланный `testId: null` за «не менять» (`courseLessons.ts:189`), потому что `LessonForm.tsx:46` ставит `null` жёстко после спреда `...defaultValues` и иначе рвал бы связь на каждом сохранении. Отличить «ключа нет» от «прислали null» сервер уже умеет — `captureLessonUpdateFields`. Когда форма урока получит поле выбора теста (ТЗ 7.13), правило меняется на «нет ключа — не менять, null — отвязать»; правка сервера и снятие `testId: null` с формы обязаны идти одним коммитом. Хвост двусторонний: комментарий обязан лечь в оба места, каждый со ссылкой на второе.
- **Инвариант «у курса один итоговый тест» держится только обработчиком** — под равенство `null` частичный индекс ненадёжен, и это проверено на живой базе: две записи с `lessonId: null` индекс пропускает. Гонка двух одновременных `POST` даст второй итоговый тест; лечится удалением из состава курса. Транзакции недоступны по той же причине, что у `reorder`. Обратный случай подтверждён в срезе 06: тот же приём с условием `status: "active"` работает штатно, дело именно в `null`.
- **`ActionError` объявлен девятый раз, по локальной копии на файл** — `TestAttemptForm.tsx`, `LessonList.tsx`, `TestList.tsx`, `AdminUserForm.tsx`, `AssignmentList.tsx`, `CourseEditPage.tsx`, `CourseListPage.tsx`, `LearningLessonPage.tsx`, `LessonEditPage.tsx`. Копии не идентичны: расходятся набор разбираемых `error.code` и ссылки возврата, поэтому это не механическое вынесение — общий примитив принимает разбор кодов параметром, а не хардкодит его. Дефекта нет ни в одной копии; растёт цена вычитания. Отдать той правке, которая откроет `client/src/components/ui/`. Замечено ревью клиентской половины 08.
- Восстановление после разрыва `reorder` работает не всегда, вопреки разделу 6 спеки: если вторая фаза успела записать часть номеров, в курсе смешаны положительные и отрицательные, и повторный `$mul: -1` падает на уникальном индексе уже в промежуточном шаге. Лечится сдвигом вместо умножения или транзакцией, когда Mongo поднимут replica set'ом. Подробности — в отчёте по срезу 04, пункт 4.
