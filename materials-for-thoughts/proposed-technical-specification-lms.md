# Техническое задание на разработку корпоративной LMS-платформы

**Статус документа:** проект для согласования  
**Версия:** 1.0  
**Тип проекта:** курсовой full-stack проект  
**Рабочее название продукта:** Corporate Learning  

## 1. Общие сведения

### 1.1. Назначение документа

Документ определяет состав, границы и правила реализации MVP веб-приложения для внутреннего обучения сотрудников. Требования сформированы на основании анкеты, описания проекта, перечня экранов, технических требований курса и приложенных эскизов интерфейса.

Документ является основой для проектирования, разработки, тестирования и приемки приложения. Все функции, прямо не включенные в настоящий документ, считаются не входящими в MVP.

### 1.2. Назначение системы

Система предназначена для компаний и отдельных подразделений, которым требуется собственная управляемая платформа обучения без обязательной зависимости от внешнего облачного LMS-сервиса.

Система должна обеспечивать полный базовый цикл корпоративного обучения:

1. создание учетной записи и вход пользователя;
2. разграничение доступа по ролям;
3. создание и публикацию учебных курсов;
4. назначение курсов сотрудникам;
5. прохождение уроков и тестов;
6. фиксацию индивидуального прогресса;
7. просмотр результатов и базовой аналитики.

### 1.3. Цель MVP

Разработать работоспособное клиент-серверное веб-приложение, демонстрирующее основные сценарии LMS и обязательные компетенции курсового проекта: маршрутизацию и закрытые страницы, формы и валидацию, управление состоянием, CRUD-операции, серверное API, middleware, MongoDB, регистрацию и авторизацию.

### 1.4. Границы MVP

В MVP входят:

- регистрация, вход и выход;
- роли «Обучающийся», «Преподаватель» и «Администратор»;
- профиль пользователя;
- индивидуальное назначение курсов обучающимся;
- каталог курсов для сотрудников, работающих с контентом;
- создание, просмотр, редактирование, публикация, архивирование и удаление допустимых сущностей;
- создание уроков с текстовыми материалами, внешним видео и ссылками на дополнительные ресурсы;
- тесты с одним или несколькими правильными ответами;
- последовательное прохождение уроков;
- сохранение прогресса и результатов тестов;
- базовая статистика по платформе, курсам и обучающимся;
- обработка загрузки, пустых состояний, ошибок, отсутствия прав и несуществующих адресов.

В MVP не входят:

- массовое назначение курсов группам и отдельный интерфейс управления группами;
- свободные ответы и ручная проверка заданий;
- загрузка, перекодирование и потоковая передача видео;
- видеоконференции, вебинары и календарь занятий;
- уведомления по email, push-уведомления и внутренний чат;
- сертификаты;
- импорт и экспорт отчетов;
- платежи;
- интеграции с внешними корпоративными системами;
- многоорганизационная архитектура;
- продвинутая BI-аналитика;
- полноценная мобильная версия.

## 2. Термины и определения

- **Обучающийся** — пользователь, которому назначают курсы и который проходит уроки и тесты.
- **Преподаватель** — пользователь, который создает и редактирует учебный контент, но не управляет пользователями и их ролями.
- **Администратор** — пользователь с полными правами управления системой.
- **Курс** — упорядоченная учебная программа, состоящая из уроков и при необходимости итогового теста.
- **Урок** — единица курса с учебными материалами и необязательным тестом.
- **Назначение курса** — связь между обучающимся и курсом, открывающая доступ к прохождению.
- **Прогресс курса** — доля завершенных опубликованных уроков курса.
- **Попытка тестирования** — зафиксированный набор ответов пользователя и рассчитанный сервером результат.
- **Публикация** — перевод курса из черновика в состояние, доступное назначенным обучающимся.
- **Архивирование** — логическое исключение сущности из активной работы без потери связанной истории.

## 3. Роли и права доступа

### 3.1. Общие правила

- Неавторизованный пользователь имеет доступ только к регистрации, входу и страницам ошибок.
- После самостоятельной регистрации пользователь получает роль «Обучающийся».
- Назначать и изменять роли может только администратор.
- Ограничения должны проверяться и на клиенте, и на сервере. Скрытие кнопки в интерфейсе не считается достаточной защитой.
- При прямом переходе на закрытый маршрут авторизованный пользователь без нужной роли должен увидеть страницу «Нет доступа».
- Неавторизованный пользователь при переходе на закрытый маршрут должен быть перенаправлен на страницу входа. После успешного входа допускается возврат на исходный маршрут, если роль дает к нему доступ.
- Заблокированный пользователь не может войти в систему. Действующая сессия такого пользователя должна перестать давать доступ к защищенным операциям.

### 3.2. Матрица прав

| Возможность | Обучающийся | Преподаватель | Администратор |
|---|:---:|:---:|:---:|
| Редактировать собственный профиль | Да | Да | Да |
| Видеть назначенные себе курсы | Да | При наличии назначения | При наличии назначения |
| Проходить назначенный курс и тесты | Да | При наличии назначения | При наличии назначения |
| Просматривать каталог учебного контента | Нет | Да | Да |
| Создавать курсы, уроки и тесты | Нет | Да | Да |
| Редактировать собственные курсы | Нет | Да | Да |
| Редактировать чужие курсы | Нет | Нет | Да |
| Публиковать и архивировать собственные курсы | Нет | Да | Да |
| Управлять пользователями и ролями | Нет | Нет | Да |
| Назначать курсы пользователям | Нет | Нет | Да |
| Просматривать общую и индивидуальную статистику | Только собственную | Нет | Да |
| Просматривать административную главную | Нет | Нет | Да |

## 4. Бизнес-правила

### 4.1. Пользователи

- Email является уникальным идентификатором входа и хранится в нормализованном виде: без пробелов по краям и в нижнем регистре.
- Пароль никогда не хранится и не возвращается в открытом виде.
- Пользователь не может самостоятельно изменить свою роль или статус.
- Администратор не может заблокировать или понизить роль собственной активной учетной записи через обычную форму редактирования.
- Удаление пользователя, имеющего историю обучения, выполняется как архивирование; статистическая история сохраняется.
- Поле «Группа» в MVP допускается как необязательная текстовая характеристика пользователя для фильтрации. Создание групп как самостоятельных сущностей и назначение курсов группам не реализуются.

### 4.2. Курсы и уроки

- Курс имеет состояния `draft` (черновик), `published` (опубликован) и `archived` (архивный).
- Новый курс создается в состоянии `draft`.
- Для публикации курс должен иметь название, категорию, уровень, краткое описание и хотя бы один опубликованный урок.
- Назначенному обучающемуся доступен только опубликованный курс.
- Изменение опубликованного курса не должно удалять уже сохраненный прогресс.
- Уроки имеют явный порядковый номер. Два активных урока одного курса не могут иметь одинаковый номер.
- Прохождение уроков последовательное: первый опубликованный урок доступен сразу, следующий открывается после завершения предыдущего.
- Урок без обязательного теста завершается по действию пользователя «Урок пройден».
- Урок с обязательным тестом считается завершенным только после получения проходного результата по тесту.
- Удаление опубликованного курса с назначениями или прогрессом запрещено. Вместо этого курс архивируется.
- Черновик курса без назначений и прогресса можно удалить после подтверждения.

### 4.3. Назначения и прогресс

- Курс назначается конкретному активному пользователю с ролью «Обучающийся».
- Повторное активное назначение того же курса тому же пользователю запрещено.
- Прогресс курса рассчитывается сервером как процент завершенных опубликованных уроков от их общего числа, округленный до целого значения.
- Курс считается завершенным, когда завершены все обязательные уроки и пройден итоговый тест, если он предусмотрен.
- Снятие назначения не удаляет накопленный прогресс. При повторном назначении прогресс восстанавливается.
- Клиент не передает на сервер готовый процент прогресса и не определяет правильность ответов; эти значения рассчитывает сервер.

### 4.4. Тестирование

- В MVP поддерживаются вопросы с одним правильным ответом и с несколькими правильными ответами.
- У каждого вопроса должно быть не менее двух вариантов и не менее одного правильного ответа.
- Для вопроса с одним правильным ответом задается ровно один правильный вариант.
- Для вопроса с несколькими правильными ответами вопрос засчитывается только при полном совпадении выбранного набора с правильным. Частичные баллы не начисляются.
- Итоговый результат равен доле правильных ответов в процентах, округленной до целого числа.
- Проходной балл задается для теста; значение по умолчанию — 70%.
- Количество попыток в MVP не ограничено. В истории сохраняются все попытки, а в сводной статистике показываются последняя и лучшая попытки.
- Правильные ответы не передаются обучающемуся до отправки попытки. После отправки отображаются результат, статус «пройден/не пройден» и количество правильных ответов; подробный разбор является необязательным расширением.

## 5. Общие требования к интерфейсу

### 5.1. Компоновка

- Авторизованная часть приложения состоит из боковой навигации и основной области контента.
- Набор пунктов боковой навигации зависит от роли.
- Для обучающегося обязательны пункты «Мое обучение», «Личный кабинет» и «Выйти».
- Для преподавателя обязательны пункты «Каталог курсов», «Мои курсы», «Личный кабинет» и «Выйти»; «Мои курсы» допускается реализовать фильтром каталога.
- Для администратора обязательны пункты «Главная», «Каталог курсов», «Пользователи» и «Выйти».
- Активный раздел визуально выделяется.
- Для вложенных страниц должна быть доступна понятная навигация назад или хлебные крошки.

### 5.2. Состояния интерфейса

Каждый экран, получающий данные с сервера, должен иметь:

- состояние первоначальной загрузки;
- состояние выполнения изменяющей операции;
- сообщение при отсутствии данных;
- понятное сообщение при ошибке;
- возможность повторить запрос там, где это уместно;
- защиту от повторной отправки формы во время запроса.

После успешного создания, изменения, удаления, назначения или прохождения теста пользователь должен получить визуальное подтверждение. Ошибки валидации отображаются рядом с соответствующими полями, серверная ошибка формы — в общей области формы.

### 5.3. Формы

- Поля имеют постоянные текстовые подписи; placeholder не заменяет подпись.
- Обязательные поля отмечаются визуально.
- Кнопка отправки недоступна при заведомо невалидной форме или во время запроса.
- При уходе со страницы с несохраненными изменениями пользователь получает предупреждение.
- Удаление и архивирование подтверждаются в модальном окне, которое блокирует взаимодействие с фоном и корректно управляется с клавиатуры.

### 5.4. Таблицы и списки

- Каталоги пользователей и курсов поддерживают серверную пагинацию.
- Рекомендуемый размер страницы — 10 записей; пользователь может выбрать 10, 20 или 50.
- Поиск запускается автоматически после паузы 500 мс и сбрасывает номер страницы на первый.
- Изменение фильтров и сортировки обновляет данные без полной перезагрузки страницы.
- Если записей не больше выбранного размера страницы, пагинация скрывается.

## 7. Функциональные требования по страницам

### 7.1. Авторизация

**Содержание:** логотип или название системы, email, пароль, кнопка «Войти», ссылка на регистрацию, область сообщения об ошибке.

**Поведение:**

- email проверяется на обязательность и формат;
- пароль обязателен;
- после успешного входа обучающийся направляется в «Мое обучение», преподаватель — в каталог курсов, администратор — на административную главную;
- при неверных данных выводится единое сообщение «Неверный email или пароль», не раскрывающее существование учетной записи;
- заблокированному пользователю выводится отдельное сообщение о блокировке;
- уже авторизованный пользователь при открытии `/login` перенаправляется на свою стартовую страницу.

### 7.2. Регистрация

**Содержание:** имя, email, пароль, повтор пароля, кнопка «Зарегистрироваться», ссылка на вход, область ошибок.

**Валидация:**

- имя: от 2 до 80 символов;
- email: корректный формат, не более 254 символов;
- пароль: от 8 до 72 символов, минимум одна буква и одна цифра;
- повтор пароля должен совпадать с паролем;
- email не должен быть занят.

**Поведение:** после успешной регистрации пользователь получает роль «Обучающийся», автоматически входит в систему и переходит на `/learning`.

### 7.3. Ошибка / нет доступа

Для несуществующего маршрута отображается код 404, краткое пояснение и переход на доступную стартовую страницу. Для отказа в доступе отображается код 403, пояснение и действие «Вернуться» или «Войти под другой учетной записью».

### 7.4. Мое обучение

**Содержание:** приветствие, количество назначенных курсов, суммарное время обучения при наличии данных, общий прогресс, список назначенных курсов.

Карточка курса содержит обложку или заглушку, название, краткое описание, прогресс, статус и кнопку «Начать» или «Продолжить». Архивный курс, ранее назначенный пользователю, может отображаться только для просмотра истории и не должен начинать новые попытки.

Общий прогресс пользователя рассчитывается как среднее значение прогресса по активным назначениям. При отсутствии назначений выводится отдельное пустое состояние.

### 7.5. Назначенный курс

**Содержание:** обложка, название, описание, категория, уровень, автор, общий прогресс, упорядоченный список уроков, итоговый тест при наличии.

Для каждого урока отображаются название, порядковый номер и состояние: «завершен», «доступен», «заблокирован». Кнопка «Продолжить обучение» открывает первый доступный незавершенный урок; если курс завершен, открывается обзор курса.

Пользователь не может открыть неназначенный курс или заблокированный урок подменой URL.

### 7.6. Урок

**Содержание:** оглавление курса, название урока, текстовый материал, внешнее видео при наличии, ссылки на дополнительные материалы, отметка завершения или переход к тесту, кнопка следующего урока.

**Поведение:**

- содержимое выводится безопасно, без исполнения произвольных скриптов;
- внешнее видео может быть представлено ссылкой или встроенным проигрывателем только для разрешенных URL;
- урок без теста завершается после подтвержденного действия пользователя;
- для урока с обязательным тестом вместо окончательного завершения предлагается пройти тест;
- после завершения обновляются оглавление, прогресс курса и статистика;
- кнопка следующего урока активна только после выполнения условий текущего урока.

### 7.7. Тестирование

**Содержание:** название теста, принадлежность к курсу/уроку, номер текущего вопроса, общий прогресс, текст вопроса, варианты ответа, кнопки перехода и отправки.

**Поведение:**

- ответы сохраняются в состоянии формы при перемещении между вопросами;
- для одиночного выбора используются радиокнопки, для множественного — флажки;
- перед окончательной отправкой показывается число вопросов без ответа и запрашивается подтверждение, если такие вопросы есть;
- сервер создает попытку, рассчитывает балл и возвращает результат;
- после отправки попытку нельзя изменить;
- успешный результат разблокирует дальнейшее прохождение, если тест является обязательным;
- повторная попытка создается как новая запись.

### 7.8. Личный кабинет

**Содержание:** имя, email, роль, необязательная группа, суммарное время обучения, число завершенных уроков, активные и завершенные курсы, прогресс по курсам, активность за последние четыре недели.

Показатели формируются из серверных данных. При отсутствии данных график заменяется понятным пустым состоянием. Из кабинета доступен переход к редактированию профиля.

### 7.9. Редактирование профиля

Пользователь может изменить имя и email, а также задать новый пароль с подтверждением. Для смены пароля требуется текущий пароль. При смене email проверяется уникальность. После успешного сохранения глобальные данные текущего пользователя обновляются без повторного входа, кроме случая, когда политика реализации требует обновить сессию после смены пароля.

### 7.10. Главная администратора

**Содержание:** количество активных курсов, пользователей и тестов; число активных назначений; количество новых пользователей за последние семь дней; число завершенных курсов; средний прогресс; список недавно созданных курсов; быстрые действия.

Быстрые действия ведут к созданию курса, управлению пользователями и статистике. Карточки и показатели должны быть основаны на реальных агрегированных данных API.

### 7.11. Каталог курсов

**Содержание:** поиск, фильтры по категории, уровню, статусу и автору для администратора, сортировка, кнопка добавления, таблица или карточки курсов, пагинация.

Для курса отображаются название, категория, уровень, количество уроков, статус, автор и доступные действия. Преподаватель может изменять только собственный курс. Администратор видит и изменяет все курсы.

Операции:

- создать курс;
- открыть редактирование;
- опубликовать при выполнении условий;
- архивировать;
- удалить допустимый черновик после подтверждения.

### 7.12. Создание и редактирование курса

**Поля:** название, категория, уровень, краткое описание, полное описание, URL обложки, статус и упорядоченный список уроков.

**Валидация:**

- название: 3–120 символов;
- категория: обязательное значение из справочника или нормализованная строка 2–60 символов;
- уровень: `beginner`, `intermediate` или `advanced`;
- краткое описание: 20–300 символов;
- полное описание: до 10 000 символов;
- URL обложки: корректный `http`/`https` URL либо пустое значение.

Уроки можно добавлять, удалять в рамках правил и менять их порядок. Сохранение курса и публикация являются разными действиями. Ошибка публикации должна объяснять, какие условия не выполнены.

### 7.13. Создание и редактирование урока

**Поля:** название, порядковый номер, текстовое содержание, URL внешнего видео, список ссылок на дополнительные материалы, признак обязательности, связанный тест.

**Валидация:** название 3–150 символов; содержание обязательно и не превышает 50 000 символов; ссылки должны иметь протокол `http` или `https`; выбранный тест должен принадлежать тому же курсу.

Редактор форматированного текста допускается, но сервер обязан очистить сохраняемую разметку от небезопасных элементов. Если редактор не используется, допускается Markdown с безопасным рендерингом.

### 7.14. Управление пользователями

**Содержание:** поиск по имени и email, фильтры по роли, статусу и группе, таблица, пагинация, переход к карточке пользователя.

Для пользователя отображаются имя, email, роль, группа, статус и доступные действия. Администратор может:

- изменить имя, роль, группу и статус;
- назначить или снять курс;
- просмотреть текущие назначения;
- перейти к статистике обучающегося;
- архивировать учетную запись согласно бизнес-правилам.

Изменение роли и статуса требует подтверждения. Пароль пользователя в административной форме не отображается.

### 7.15. Статистика пользователей

**Содержание:** фильтры по курсу, группе и статусу; количество пользователей; число активных пользователей; число завершивших курсы; средний прогресс; средний прогресс по курсам; таблица обучающихся.

Активным считается пользователь, совершивший учебное действие за последние 30 календарных дней. Таблица содержит имя, группу, число активных и завершенных курсов, средний прогресс и ссылку на детальную статистику.

### 7.16. Статистика одного ученика

**Содержание:** данные пользователя, средний прогресс, число завершенных курсов, назначенные курсы, результаты тестов и последние учебные действия.

Для результата теста отображаются тест, дата, балл, статус и номер попытки. История активности включает не менее следующих событий: открытие урока, завершение урока, отправка теста и завершение курса.

### 7.17. Создание и редактирование теста

**Поля теста:** название, связанный курс, необязательный связанный урок, проходной балл и список вопросов.

**Поля вопроса:** текст, тип, список вариантов, отметки правильных вариантов, порядковый номер.

Администратор и автор курса могут добавлять, редактировать, удалять и менять порядок вопросов. Тест нельзя сохранить как готовый к использованию без названия, связи с курсом и хотя бы одного валидного вопроса. Изменения теста не должны менять результаты уже завершенных попыток; для этого в попытке сохраняется снимок необходимых данных или версия теста.

## 8. Модель данных

Ниже приведен обязательный логический состав данных. Названия коллекций и технических полей могут отличаться при сохранении смысла и связей.

### 8.1. User

- `_id`;
- `name`;
- `email` — уникальный индекс;
- `passwordHash`;
- `role`: `student | teacher | admin`;
- `groupName` — необязательное поле;
- `status`: `active | blocked | archived`;
- `lastLoginAt`;
- `createdAt`, `updatedAt`.

### 8.2. Course

- `_id`;
- `title`;
- `category`;
- `level`;
- `shortDescription`;
- `description`;
- `coverUrl`;
- `authorId` → User;
- `status`: `draft | published | archived`;
- `publishedAt`;
- `createdAt`, `updatedAt`.

### 8.3. Lesson

- `_id`;
- `courseId` → Course;
- `title`;
- `order`;
- `content`;
- `videoUrl`;
- `resourceLinks[]` с названием и URL;
- `isRequired`;
- `status`: `draft | published`;
- `createdAt`, `updatedAt`.

### 8.4. Test и Question

Test:

- `_id`;
- `courseId` → Course;
- `lessonId` → Lesson или `null` для итогового теста;
- `title`;
- `passingScore`;
- `version`;
- `questions[]`;
- `createdAt`, `updatedAt`.

Question:

- `_id` внутри теста;
- `text`;
- `type`: `single | multiple`;
- `order`;
- `options[]`: идентификатор, текст, признак правильности в административном представлении.

### 8.5. CourseAssignment

- `_id`;

- `courseId` → Course;
- `assignedBy` → User;

Для пары `userId + courseId` одновременно допускается не более одного активного назначения.

### 8.6. LessonProgress

- `_id`;
- `userId` → User;
- `courseId` → Course;
- `lessonId` → Lesson;
- `status`: `not_started | in_progress | completed`;
- `startedAt`, `completedAt`;
- `updatedAt`.

### 8.7. TestAttempt

- `_id`;
- `userId` → User;
- `testId` → Test;
- `testVersion`;
- `courseId`, `lessonId`;
- `answers[]`;
- `correctCount`, `totalCount`, `score`;
- `passed`;
- `attemptNumber`;
- `submittedAt`.

### 8.8. ActivityEvent

- `_id`;
- `userId`;
- `courseId` и `lessonId` при наличии;
- `type`;
- `metadata` с ограниченным набором безопасных полей;
- `createdAt`.

События используются для ленты активности и агрегированной статистики, но не должны содержать пароли, токены и полные наборы правильных ответов.

## 9. Требования к REST API

API использует JSON, единый префикс (например, `/api`) и корректные HTTP-методы и статусы. Минимально необходимы следующие группы маршрутов:

### 9.1. Авторизация и профиль

- `POST /auth/register`;
- `POST /auth/login`;
- `POST /auth/logout`;
- `GET /auth/me`;
- `PATCH /users/me`;
- `PATCH /users/me/password`.

### 9.2. Курсы и контент

- `GET /courses` с пагинацией, поиском, фильтрами и сортировкой;
- `POST /courses`;
- `GET /courses/:courseId`;
- `PATCH /courses/:courseId`;
- `DELETE /courses/:courseId`;
- `POST /courses/:courseId/publish`;
- `POST /courses/:courseId/archive`;
- CRUD-маршруты уроков внутри курса;
- CRUD-маршруты тестов и вопросов.

### 9.3. Обучение

- `GET /learning/me`;
- `GET /learning/courses/:courseId`;
- `GET /learning/courses/:courseId/lessons/:lessonId`;
- `POST /learning/lessons/:lessonId/start`;
- `POST /learning/lessons/:lessonId/complete`;
- `GET /learning/tests/:testId` без правильных ответов;
- `POST /learning/tests/:testId/attempts`;
- `GET /learning/me/statistics`.

### 9.4. Администрирование

- `GET /admin/dashboard`;
- `GET /admin/users`;
- `GET /admin/users/:userId`;
- `PATCH /admin/users/:userId`;
- `POST /admin/users/:userId/assignments`;
- `DELETE /admin/users/:userId/assignments/:assignmentId`;
- `GET /admin/statistics`;
- `GET /admin/statistics/users/:userId`.

### 9.5. Общий формат ответа и ошибок

Успешный список возвращает массив данных и метаданные пагинации: текущую страницу, размер страницы, общее число записей и страниц. Ошибка возвращает стабильный машинный код, понятное сообщение и при необходимости список ошибок полей.

Сервер должен использовать как минимум следующие статусы:

- `200` — успешное чтение или изменение;
- `201` — создание;
- `204` — успешная операция без тела;
- `400` — некорректный запрос;
- `401` — отсутствует или недействительна авторизация;
- `403` — недостаточно прав;
- `404` — сущность не найдена;
- `409` — конфликт уникальности или состояния;
- `422` — данные не прошли бизнес-валидацию;
- `500` — непредвиденная ошибка без раскрытия технических деталей клиенту.

## 10. Технические требования

### 10.1. Frontend

- React;
- маршрутизация на базе React Router;
- библиотека управления глобальным состоянием: Redux Toolkit и React Redux либо согласованный эквивалент;
- асинхронные операции через thunk-механизм или слой запросов выбранной библиотеки;
- формы через React Hook Form и схему валидации Yup/Zod либо согласованный эквивалент;
- переиспользуемые базовые компоненты: кнопка, поле, селект, модальное окно, loader, сообщение об ошибке, пагинация;
- кастомные хуки для повторяемой логики запросов, debounce, прав доступа или работы с формами;
- единый API-клиент и централизованная обработка ошибок авторизации;
- отсутствие хранения вычисляемых сервером прав, процентов и результатов как источника истины на клиенте.

### 10.2. Backend

- Node.js;
- Express.js;
- MongoDB;
- Mongoose;
- REST API;
- middleware для авторизации, проверки ролей, валидации, обработки ошибок и журналирования запросов;
- CRUD-операции для основных управляемых сущностей;
- индексы для уникального email, поиска и часто используемых связей;
- конфигурация через переменные окружения;
- отсутствие секретов и строк подключения в репозитории.

### 10.3. Авторизация и безопасность

- пароли хешируются алгоритмом bcrypt или Argon2;
- сессия реализуется безопасным JWT в `httpOnly` cookie либо иной согласованной схемой, исключающей доступ клиентского JavaScript к долгоживущему токену;
- cookie в production имеет флаги `Secure` и `SameSite` в соответствии со схемой размещения;
- вход ограничивается по частоте запросов;
- данные всех изменяющих запросов валидируются на сервере;
- HTML/Markdown учебных материалов очищается перед сохранением или безопасно рендерится;
- CORS разрешает только настроенные источники;
- ответы API не содержат `passwordHash`, секретов и правильных ответов для обучающегося;
- доступ к каждой сущности проверяется с учетом роли, авторства курса и назначения.

## 11. Нефункциональные требования

### 11.1. Удобство и доступность

- Основной целевой формат MVP — desktop, ширина окна от 1280 px.
- На ширине от 1024 px интерфейс не должен терять данные и ключевые действия; полноценная мобильная переработка не требуется.
- Все интерактивные элементы доступны с клавиатуры и имеют видимый фокус.
- Поля формы связаны с подписями, ошибки доступны вспомогательным технологиям.
- Контраст текста и элементов управления должен соответствовать базовым требованиям WCAG 2.1 AA.
- Иконки без текстовой подписи имеют доступное название или tooltip.

### 11.2. Производительность

- Списки используют серверную пагинацию и не загружают все документы коллекции.
- Поиск не отправляет запрос на каждый введенный символ.
- Повторные переходы не должны создавать неконтролируемые дубли запросов.
- Для типового локального набора до 1 000 пользователей, 200 курсов и 20 000 событий большинство API-запросов должно завершаться не более чем за 1 секунду без учета холодного запуска и сетевой задержки.

### 11.3. Надежность

- Необработанные ошибки не должны приводить к белому экрану приложения.
- Сервер имеет централизованный обработчик ошибок.
- Критические изменяющие операции возвращают результат только после успешного сохранения.
- Повторное нажатие кнопки не создает дубликаты пользователей, назначений, попыток или курсов.
- В репозитории предоставляются пример переменных окружения и инструкция запуска.

## 12. Начальные и демонстрационные данные

Для приемки должен быть предусмотрен воспроизводимый способ заполнения базы тестовыми данными. Минимальный набор:

- один администратор;
- один преподаватель;
- два обучающихся, один из них с частично пройденным курсом;
- не менее трех курсов: опубликованный, черновик и архивный;
- не менее пяти уроков в основном опубликованном курсе;
- не менее одного теста с одиночным выбором;
- не менее одного теста с множественным выбором;
- назначения, прогресс и попытки, достаточные для отображения статистики.

Учетные данные демонстрационных пользователей указываются в README, но не используются в production-конфигурации.

## 13. Требования к тестированию

Минимальный набор автоматизированных проверок:

- модульные тесты вычисления результата теста и прогресса курса;
- проверка регистрации, входа и отказа при неверных данных;
- проверка ролевого middleware;
- интеграционные тесты основных CRUD-операций курса;
- проверка назначения курса;
- проверка запрета доступа к неназначенному курсу и чужому курсу преподавателя;
- проверка отправки теста и сохранения попытки;
- frontend-тесты хотя бы для одной сложной формы и одного защищенного маршрута.

Перед сдачей проект должен проходить настроенные команды сборки, линтинга и тестов без ошибок.

## 14. Критерии приемки MVP

MVP считается принятым, если одновременно выполнены следующие условия:

1. Проект устанавливается и запускается по README на чистом окружении с указанными версиями инструментов.
2. Frontend взаимодействует с Express API, а постоянные данные сохраняются в MongoDB.
3. Новый пользователь может зарегистрироваться, войти, выйти и изменить профиль.
4. Доступ к страницам и API действительно ограничен ролями.
5. Администратор может найти пользователя, изменить его роль/статус и назначить ему опубликованный курс.
6. Преподаватель может создать собственный курс, добавить урок и тест, отредактировать их и опубликовать валидный курс.
7. Преподаватель не может редактировать чужой курс и управлять пользователями.
8. Обучающийся видит назначенный курс, проходит доступные уроки по порядку и не может открыть заблокированный урок прямой ссылкой.
9. Результат теста рассчитывается на сервере, сохраняется как отдельная попытка и влияет на завершение обязательного урока.
10. Прогресс сохраняется после обновления страницы и повторного входа.
11. Администратор видит общую статистику и детальную статистику выбранного ученика.
12. Поиск, фильтры, сортировка и пагинация каталогов работают совместно.
13. Формы имеют клиентскую и серверную валидацию, а ошибки отображаются без потери введенных данных, где это безопасно.
14. На страницах предусмотрены loader, пустое состояние и обработка ошибок.
15. Несуществующий адрес открывает 404, а запрещенный маршрут — 403 или корректное перенаправление согласно правилам авторизации.
16. Изменяющие и опасные операции защищены от случайного повторения и требуют подтверждения, где это установлено ТЗ.
17. В репозитории отсутствуют пароли, секреты, токены и реальные строки подключения.

## 15. Состав результата разработки

По завершении должны быть переданы:

- исходный код frontend и backend;
- схема или описание моделей данных;
- файл `.env.example` без секретов;
- скрипт или команда заполнения демонстрационными данными;
- README с требованиями к окружению, установкой, запуском, сборкой и тестированием;
- перечень демонстрационных учетных записей;
- краткое описание API или коллекция запросов;
- результаты линтинга и автоматизированных тестов.

## 16. Допущения, требующие подтверждения перед финальной фиксацией ТЗ

Настоящая версия специально фиксирует следующие решения, отсутствующие или неоднозначные во входных материалах:

1. Самостоятельная регистрация сразу создает активного обучающегося; отдельного подтверждения email нет.
2. Курсы назначаются отдельным пользователям; полноценные группы отнесены за границы MVP.
3. Преподаватель управляет только собственными курсами, администратор — всеми.
4. Прохождение уроков последовательное.
5. Проходной балл теста по умолчанию равен 70%, количество попыток не ограничено.
6. Процент курса рассчитывается по завершенным опубликованным урокам; обязательный тест влияет на факт завершения урока или курса.
7. Файлы и видео не загружаются в собственное медиахранилище; в уроках используются текст, внешнее видео и ссылки на материалы.
8. Desktop является основным форматом MVP; мобильная версия остается развитием проекта.
9. Удаление сущностей с историей заменяется архивированием, чтобы не разрушать статистику.

После согласования этих пунктов раздел можно сохранить как журнал принятых проектных решений либо перенести решения в соответствующие обязательные требования.
