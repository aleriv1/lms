# Slice 13 — сервер

## 1. Что сделано

- Лимитер после `validate(loginBodySchema)`: независимые ключи email/IP, пределы 5/20, фиксированное окно 15 минут от первого отказа. Запись только в ветках `invalid_credentials`; отказ 429 не увеличивает счётчик. Ответ содержит `rate_limited`, русское сообщение и `Retry-After` по более позднему сроку заполненных счётчиков.
- Просроченные записи удаляются при проверке; при превышении 10 000 ключей после очистки хранилище сбрасывается. Ограничения одного процесса описаны в комментарии. Новых зависимостей, переменных окружения и `trust proxy` нет.
- Для неизвестного email используется мемоизированный Promise хеша случайного значения, созданного через `hashPassword`; проверка пароля вызывается до проверки наличия пользователя. Общий экземпляр ошибки заменён фабрикой.
- В shared добавлены схемы/типы разбора и обязательный `review`. `buildAttemptReview` использует снимок, нормализованные ответы и существующий `isQuestionCorrect`. POST возвращает разбор тех же значений, которые записаны в попытку.
- `clearDatabase` сбрасывает процессное состояние лимитера. В единственном разрешённом клиентском файле добавлена ровно одна строка `review: []`.
- Добавлены проверки порогов email/IP, сброса, фиксированного окна, позднего срока двух счётчиков, переполнения Map и нормализации email. Разбор проверен для правильных, частично неправильных, пропущенных и неизвестных вариантов; HTTP проверяет порядок, флаги и согласованность с оценкой.

## 2. Отступления и противоречия

- Решение 1 сначала требует сбрасывать оба счётчика сразу после проверки пароля, до blocked/archived, а затем запрещает сброс для blocked. Выбран явный порядок и пример решения 4: сброс до проверки статуса. Поэтому правильный пароль blocked очищает счётчики; archived сначала очищает их, затем записывает один отказ. Повторные archived-входы с правильным паролем не накапливают пять отказов. Это следствие выбранного прочтения, а не выполнение обоих противоречащих требований.
- Фраза «успешный пользователь никогда не ограничивается» не совместима с проверкой лимита до проверки пароля. Реализован заданный middleware-gate: при заполненном счётчике любой запрос получает 429 до истечения окна, даже с правильным паролем.
- Дополнительно изменён `server/src/contracts/sharedContracts.test.ts`: одна строка `review: []` в существующей фикстуре. Первый запуск gate выявил её падение после обязательного изменения контракта; этот файл отсутствует в списке промпта. Других дополнительных исходников нет.
- Prettier отформатировал затронутые серверные/shared-файлы, включая несколько существующих длинных строк.
- Вводная промпта обещает закрыть три из четырёх пунктов 18.3, но timing tail не является пунктом этого списка: там также есть предупреждение об уходе с несохранёнными изменениями. Реализован перечисленный серверный объём; клиентское предупреждение и WCAG не проверялись и не изменялись. Раздел 18.3 ТЗ описывает прежний состав недоделанного, но прямо сохраняет требования; сам документ не изменён.

## 3. Что не выполнено и ограничения

Блокеров реализации нет. Ручные проверки оставлены разработчику. Браузер, dev-сервер и seed не запускались; дополнительных данных вне автоматических тестов не создавалось. Все запущенные команды завершились.

По заданному алгоритму первый запрос к неизвестному аккаунту дополнительно вычисляет случайный хеш; последующие используют готовый Promise. Исправление устраняет пропуск bcrypt-сравнения, но не обещает равенство времени всего HTTP-запроса. Замеров времени и timing-assertions нет. Лимитер считает завершившиеся отказы: одновременно прошедшие gate запросы могут превысить порог. Map локален процессу, сбрасывается при рестарте и fail-open переполнении.

## 4. Замеченное вне объёма

Сборка предупреждает об аннотациях в Zod и клиентском JS-чанке больше 500 kB; завершается успешно. Статусные противоречия и расхождение описания 18.3 приведены выше для исправления промпта. Пользовательский `.claude/settings.local.json`, присутствовавший до начала работы, не включён в срез.

## Проверить руками

Исходное состояние: приложение запущено разработчиком, база содержит текущий seed, у используемых адресов/IP нет активного ограничения (иначе дождаться 15 минут). Начальная страница [http://localhost:5173/login](http://localhost:5173/login). Для серверных полей открыть DevTools → Network → Fetch/XHR; смотреть Response и Headers соответствующего запроса.

Фактический URL `/learning/tests/...` взять из адресной строки, идентификатор не собирать. Успех: GET `/api/learning/tests/...` содержит вопрос «Когда заполняется журнал осмотров?» и варианты, но нигде в Response нет `isCorrect`.
3. На URL теста из п. 2 выбрать «В конце месяца», нажать «Отправить ответы». Успех: POST с окончанием `/attempts` возвращает 201, score 0, correctCount 0, totalCount 1; review содержит один неправильный вопрос. 4. На том же URL нажать «Пройти ещё раз», выбрать «Сразу после осмотра», отправить. Успех: 201, score 100, correctCount 1; вопрос review правильный, правильный вариант выбран. Повторить с пустым выбором и подтвердить отправку без ответа: 201, score 0, вопрос неправильный, все isSelected false.
