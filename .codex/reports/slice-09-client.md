## 2. Расхождение с промптом

Промпт, строка 76, обещает `422 validation_error` для неразбираемого
идентификатора без различия между query и параметром пути. Фактически:

- `GET /api/admin/statistics?courseId=nope` — `422 validation_error`;
- `GET /api/admin/statistics?pageSize=11` — `422 validation_error`;
- `GET /api/admin/statistics/users/nope` — **`404 not_found`**, сообщение
  «Страница не найдена», а не обещанный отказ валидации.

Основание: `server/src/routes/adminStatistics.ts:259` вызывает
`validate(userParamsSchema, "params")`; `server/src/middleware/validate.ts:28`
отдельно возвращает для `params` 404. `errorHandler.ts` сохраняет статус и
код `AppError` в ответе. Это вывод по исходникам, не результат HTTP-прогона.

Применено явное условие предварительной проверки промпта «read the server,
then stop if it disagrees»: отчёт без клиентского кода. Это расхождение
промпта с фактическим отказом API, а не выбор новой трактовки требований ТЗ.
Сервер, shared и сам промпт не изменялись.

Для продолжения достаточно уточнить в промпте: некорректные query-параметры
дают 422, некорректный `userId` в пути — 404, как и отсутствующий пользователь.
Либо явно разрешить продолжить клиент с текущим серверным поведением.
